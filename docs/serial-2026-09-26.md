# Serial devices in containers (draft)

Status: draft, 2026-09-26; the four review questions decided the same day. Nothing built. Written against the bench kit on order: a Home Assistant Connect ZBT-2, a ThirdReality USB-C Zigbee dongle, a ThirdReality colour bulb (ZL4) and a ThirdReality temperature and humidity sensor (Lite). Facts marked *(on arrival)* are to be read off the hardware, not trusted from datasheets.

## What it is for

Home Assistant, Zigbee2MQTT and their kind run in containers and talk to a radio stick over a serial port: `devices: [/dev/serial/by-id/usb-…-if00]` in a compose file. On a Mac that stick is a USB device the Mac owns, and no Mac container runtime can hand it to a container, so the answer today is "run Home Assistant on a Pi". The ask (Reddit, kylewhirl) is to run the same compose file on lighter with the stick plugged into the Mac.

Every stick in this category is a serial port to Linux: Zigbee (EmberZNet's EZSP over ASH, or ZNP), Thread (Spinel for an OpenThread border router), Z-Wave (Z-Wave JS), and further out a 3D printer's controller or an ESPHome board. So the feature is **a Mac serial port as a Linux tty**, not USB; the kit exists to prove it on the two kinds of USB-serial bridge a user is likely to own.

## The bench

| Device | Role | What it exercises |
|---|---|---|
| Home Assistant Connect ZBT-2 | Coordinator | Silicon Labs MG24 behind an ESP32-S3 acting as the USB bridge (CDC-ACM on the Mac, `/dev/cu.usbmodem…`), 460800 baud, RTS/CTS hardware flow control. The stick people are asking about. |
| ThirdReality USB-C Zigbee dongle | Coordinator | An EFR32 behind a USB-UART bridge chip *(on arrival: chip, macOS driver, baud, flow control; expected 115200 with none)*. The other common shape, and a second stick for two ports at once. |
| ThirdReality colour bulb ZL4 | Router | Mains-powered, so it routes; instant visible proof that a command went through the whole path. |
| ThirdReality temp/humidity sensor Lite | Sleepy end device | Wakes, reports, sleeps: traffic the coordinator must not lose across long quiet spells. |

The two sticks between them cover both baud rates the Silicon Labs firmware ships at, flow control on and off, and a Mac CDC-ACM driver against a vendor-bridge driver. Thread firmware on the ZBT-2 (an OpenThread border router in a container) is the same path with a different protocol and is a stretch goal, not a gate.

## What must work

1. Bytes both ways with none lost or reordered, including when the reader in the container is slow.
2. termios reaches the real port: baud, character size, parity, stop bits, and `CRTSCTS`. ZHA's probe and the Silicon Labs flasher both change baud on an open port.
3. Modem-control lines: DTR and RTS set by the container (`TIOCMSET`, and pyserial sets both on open), CTS, DSR and DCD read by it (`TIOCMGET`), and break.
4. Exclusive: the Mac and a container never both read one port.
5. A stable name. Existing compose files name the stick by `/dev/serial/by-id/…`, and should run unchanged.
6. Unplug and replug recover without restarting the container.
7. Costs nothing while nothing is attached, and next to nothing while a radio idles.

## Decisions proposed

### 1. The transport is a second PL011, one per attached port

lighter already emulates an ARM PL011 for its console (`devices/pl011.rs`), and the guest kernel already has the driver built in (`CONFIG_SERIAL_AMBA_PL011=y`). A PL011 is a real UART to Linux: `/dev/ttyAMA1` is a tty with the whole of termios, `TIOCMGET`/`TIOCMSET`, break and modem-status interrupts, through the stock `amba-pl011` driver, and every one of those arrives in the VMM as a register write it can map onto the Mac's port. Nothing in the guest kernel changes and nothing is installed in the container.

The cost is that every data byte is a trap: the driver reads FR then DR per byte received, and FR then DR per byte sent, so two exits a byte. At the ZBT-2's line rate saturated in both directions (about 46 KB/s each way) that is some 180,000 exits a second; what that costs on the Mac is to be measured (gate m15, below) rather than guessed. What a radio actually sends is far less: a Zigbee network of a few dozen devices is hundreds of bytes a second, and the saturated case is only ever a firmware flash, which is a minute at most.

Rejected:

- **virtio-console.** Its ports (`/dev/vportNpM`) are not ttys, so `tcsetattr` fails and every serial library refuses them. Its console form (`/dev/hvcN`) is a tty but drops termios and modem lines on the floor: a baud change the Mac never hears about is a stick that stops answering.
- **A pty in the guest, fed over vsock by the agent.** termios changes are visible at the master (packet mode with `EXTPROC`), but a pty has no modem lines, so `TIOCMSET` fails; whether that breaks a given client depends on how its serial library treats the error. It would work for most of the bench and fail somewhere it is hard to diagnose.
- **A paravirtual tty driver of our own over virtio.** The efficient answer (a byte costs nothing, a batch costs one kick), and a kernel driver to carry and own with no upstream to send it to. Kept as the fallback if m15 shows the exits matter, and the PL011 register mapping below is what it would forward.
- **USB passthrough as the default.** Taking a device from the Mac's driver needs root or Apple's `com.apple.vm.device-access` entitlement, and a serial stick does not need it. It is the right answer for non-serial devices, and is planned as a second backend ("Later: raw USB").

### 2. The Mac side is the port's own file descriptor

The VMM opens `/dev/cu.*` (not `tty.*`, which blocks on carrier) non-blocking, takes `TIOCEXCL`, and maps the guest's registers onto it:

| Guest writes or reads | The VMM does |
|---|---|
| `IBRD`/`FBRD`, latched by the `LCR_H` write as on hardware | baud = 24 MHz / (16 × (IBRD + FBRD/64)), snapped to the nearest standard rate within 3% (460800 comes out as 461538), set with `cfsetspeed`, or `IOSSIOSPEED` for a non-standard rate |
| `LCR_H` word length, parity, stop bits | `CSIZE`, `PARENB`/`PARODD`, `CSTOPB` |
| `LCR_H.BRK` | `TIOCSBRK` / `TIOCCBRK` |
| `CR.RTSEn`/`CR.CTSEn` (the driver's `CRTSCTS`) | `CRTSCTS` on the Mac's port |
| `CR.DTR`/`CR.RTS` | `TIOCMBIS` / `TIOCMBIC` |
| `FR.CTS`/`DSR`/`DCD`/`RI` | the Mac's `TIOCMGET`, cached; a change raises the modem-status interrupt |

**Flow control is end to end, and nothing is dropped.** Between the stick and the Mac, RTS/CTS is the Mac driver's job once `CRTSCTS` is set. Between the Mac and the guest it is back-pressure: when the guest's receive FIFO is full the VMM stops reading the Mac's port, the Mac driver's buffer fills, and it deasserts RTS to the stick. When the Mac's port will not take a byte (the stick deasserted CTS), the VMM reports `TXFF`, and the guest driver waits for the TX interrupt as it would on hardware. The console PL011 does neither (it drops input past 4096 bytes and never sets `TXFF`, both right for a console); the serial one is a mode of the same device, not a copy.

macOS has no `TIOCMIWAIT`, so input lines are polled: every 20 ms while the guest has the port open (`CR.UARTEN`), never while it is closed. Nothing on the bench signals on those lines in normal running; they matter for carrier on unplug (below) and for flashers that read them.

### 3. Attaching is per machine, named by the stick, and survives a replug

```
lighter usb list                         # the Mac's USB serial ports: path, vendor, product, serial number
lighter usb attach                       # with exactly one known radio stick plugged in, that one
lighter usb attach zbt-2                 # by product, serial number or /dev/cu path; persisted
lighter usb detach zbt-2
```

The command is `usb` because that is what people search for and how the ask was put; `list` and the help say plainly that serial devices work and other USB devices do not (yet, see "Later: raw USB"). The CDI name stays `lighter.sh/serial`, because inside Linux that is what it is.

- **Per machine, not per container.** The stick is plugged into the Mac, and a Home Assistant container is recreated on every upgrade and `compose up`; an attachment keyed to a container would need a lighter step each time and break on a new container id. Attached once, the compose file alone says which container uses it, and the tty's exclusive open keeps two containers off one stick, as on a Pi.
- **A bare `attach` picks the obvious stick.** With exactly one device plugged in whose USB IDs are a known Zigbee, Thread or Z-Wave radio (a short table: the Nabu Casa sticks, Sonoff, ThirdReality, the Silicon Labs and TI reference designs, Zooz, Aeotec), `lighter usb attach` attaches it; with none or several it lists them and asks for a name. The instructions for Home Assistant are then one command and an unchanged compose file.

- **Four UART slots at boot**, in the device tree whether used or not, because the tree cannot change after boot. An empty slot is a port with no carrier. Attaching fills a slot without a restart; a fifth stick waits for a detach.
- **The guest names the stick as Linux would.** The Mac's IORegistry has the USB vendor, product and serial number strings, and the agent makes `/dev/serial/by-id/usb-<vendor>_<product>_<serial>-if00` point at the slot's `ttyAMA`, the name udev would give it on a Pi. A compose file written for a Pi then runs unchanged: `docker run --device /dev/serial/by-id/…` resolves the link in the guest. A CDI name (`lighter.sh/serial=zbt-2`) is offered too, for those who would rather not write a serial number into a compose file.
- **Unplug keeps the tty.** The VMM watches IOKit for the port going away; it closes the Mac fd and drops DCD, DSR and CTS, which a client sees as the stick going silent (ZHA and Zigbee2MQTT then reconnect on their own watchdogs). When a stick with the same serial number returns, the VMM reopens it, reapplies the last termios and lines, and raises carrier. The node in the container never goes away, which is better than a Pi, where a replug makes a new one.
- **In use elsewhere is a refusal with a reason.** If a Mac app holds the port (the web flasher in Chrome, `screen`), attach fails naming the process, and never steals it.

### 4. Firmware is flashed on the Mac

The Home Assistant web flasher works in Chrome over Web Serial with the stick plugged into the Mac, and needs nothing from lighter. Home Assistant's own hardware integration for the ZBT-2 (the one that offers to switch it between Zigbee and Thread) finds the stick by its USB IDs in sysfs, and the guest has no USB bus, so it will not offer itself; ZHA and Zigbee2MQTT, given the by-id path, work. Documented as a limit rather than faked: a fake USB tree in sysfs is a lie some tool would eventually act on. Raw USB (below) removes the limit honestly.

## Verification

- **Unit tests:** the baud arithmetic (every standard rate round-trips through IBRD/FBRD), the register-to-ioctl mapping, back-pressure in both directions with no byte dropped, and the slot model (attach, detach, replug to the same slot).
- **Gate m15, no hardware:** a pty pair on the Mac stands in for the stick. The container runs pyserial against `/dev/ttyAMA1`, the Mac end echoes, and the gate checks: 10 MB each way at 460800 with a byte-exact comparison; a slow reader in the container for 30 s with nothing lost; baud changes seen at the Mac end (`tcgetattr` on the pty); the VMM's CPU at a saturated line and while open and idle; and nothing polled while no port is open. Modem lines need real hardware, since a pty has none.
- **Gate m15, the kit:** Zigbee2MQTT and ZHA (Home Assistant's container) in turn, on each stick. Form a network, pair the bulb and the sensor, toggle the bulb 1000 times and count the acknowledgements, keep the sensor's reports for 12 hours with none missing that its reporting interval promises, unplug and replug the stick mid-run and see both recover, and both sticks attached at once. The same run on a Pi or a Linux box with the same sticks is the baseline for the counts.
- **The Reddit reply** is the compose file from the hardware gate, unchanged but for the path.

## Decided in review

1. **PL011 now**, a paravirtual tty driver only if m15 says the exits matter. The number to watch is an open, idle port's cost on the Mac, which runs around the clock; a saturated line is only ever a flash, and flashing happens on the Mac.
2. **`lighter usb`**, with the CDI name `lighter.sh/serial` (section 3).
3. **Four slots.** Zigbee, Thread, Z-Wave and a spare; more costs a restart to add, and a restart is cheap.
4. **Per machine** (section 3).

## Later: raw USB

The serial path uses the Mac's own driver and needs no privilege, which is why it is the default. A second backend behind the same command, `lighter usb attach --raw`, would hand the guest the USB device itself:

- **Capture.** IOKit lets a process take a USB device from its macOS driver (re-enumerate with the capture option; what libusb's `detach_kernel_driver` uses on macOS since 1.0.25). It needs the `com.apple.vm.device-access` entitlement or root. The VMM stays unprivileged: a small root helper (a launchd daemon, installed with the person's consent) captures the device and serves it over a socket. Whether root alone still suffices on macOS 26 is the first thing to check, on the ThirdReality stick.
- **Transport: USB/IP.** The guest attaches through `vhci-hcd`, upstream since Linux 3.17, so no kernel driver of ours; USB/IP carries URBs, so every class works and Linux's own drivers (`cdc_acm`, `cp210x`, `ch341`, anything else) bind as they would on a Pi.
- **What it buys.** Any USB device (a Coral, an SDR, a UPS), and a raw radio stick whose USB IDs are really in the guest's sysfs, so Home Assistant's hardware integration finds a ZBT-2 and offers its firmware switch.
- **What it costs.** A root daemon is its own security design: who may ask it to capture what, over which socket, and a guarantee that the Mac's keyboard, disks and Apple devices are never on the list. A captured device is gone from the Mac until detach re-enumerates it. Each transfer is a round trip over vsock, fine for these devices and wrong for a webcam.

The slot model does not carry over (USB/IP needs no UART), but the naming, the per-machine attachment and the replug rules do, so the CLI and config are designed once for both.
