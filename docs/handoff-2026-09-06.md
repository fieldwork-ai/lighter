# Handoff, 2026-09-06: lighter after 0.4.0

Written for whoever picks lighter up next. It says where the project stands, how the work is done day to day, every open thread with the evidence behind it and a way in, and the traps that cost hours this week. The worklog (`docs/worklog.md`) is the primary record: every row is one experiment with numbers and a verdict, and every claim below has a row behind it. `docs/architecture.md` says how the machine is built and why; `docs/releasing.md` is the release procedure. Read those three before changing anything.

## 1. Where things stand

**Released.** lighter 0.4.0 shipped on 2026-09-06 at about 17:05: tag `v0.4.0` on commit `8d39028`, a notarized tarball `lighter-0.4.0-arm64.tar.gz` (80 MB; sha256 `a094d444a3a63a2e86881cf3bc759e06239d62fa3ad372356831c6a97d5f705b`), the GitHub release with its notes, the formula in `packaging/lighter.rb`, and the Homebrew tap (`fieldwork-ai/homebrew-tap`, PR #2, merged). The `dev → main` pull request (fieldwork-ai/lighter#2) is merged; `main` is `9778a45`. Both install paths were checked after the merges: `brew install fieldwork-ai/tap/lighter` on the M1 and the one-line installer from `main` on the M5, each through doctor, start, a container and stop.

**Branches.** All work happens on `dev`. `main` is protected and is only ever moved by a `dev → main` pull request, which is also where the release notes live in long form. Never push to `main`. CI (`.github/workflows`) runs `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all` and `bash -n` on the scripts; run those three cargo commands verbatim before every push, not the local habit.

**What 0.4.0 contains, in one paragraph each.**

- *Memory.* The guest boots with a base (a quarter of the configured memory, a gigabyte at least) and a virtio-mem range for the rest, plugged in 128 MiB blocks as containers need it and unplugged to the base when nothing runs (`crates/lighter-vmm/src/virtio/mem.rs`, `memory_policy.rs`; guest kernel patches 0024 and 0026). The range's blocks are onlined by the kernel's `auto-movable` policy at a ratio of one, which patch 0026 makes the kernel's default: a block is movable (and so can come back out) only while movable memory is at most equal to kernel-usable memory, and ordinary memory otherwise, so slab always has room. Once the range is out, the guest's agent offers what it can spare through the balloon. Every release path replaces the span's mapping (a fresh anonymous `mmap`), which is what makes the footprint macOS reports honest; 0.3.0 under-counted every page the guest reused after a `MADV_FREE_REUSABLE`.
- *Networking.* A container's TCP is carried as vsock streams, UDP as flows on one stream per direction, DNS on a framed stream to the Mac's resolver, and only ARP, DHCP and ICMP reach the virtual card, which the VMM answers itself (`crates/lighter-vmm/src/streams.rs`, `reactor.rs`, `net.rs`, `dns.rs`; `guest/agent/src/{main,udp,udp_inbound}.rs`; the nft ruleset in `guest/rootfs/init`). Published ports bind on the Mac what Docker bound in the guest, in both families, with `lighter config --publish lan|localhost`. Containers have IPv6 (a unique-local link, `dockerd --ipv6 --ip6tables`); AAAA is answered only while the Mac has a v6 route. The kernel carries nf_tables' whole expression set.
- *Platform.* The daemon publishes its identity (audit token, home inode) under the home lock, and `stop` signals pid and pidversion together; a machine started by 0.3.0 is found through the control socket's peer token and stopped the old way (`crates/lighter-cli/src/{instance,machine}.rs`). Docker API requests carry one absolute deadline (`crates/lighter-docker/src/http.rs`). One kernel ships, `6.18.49-lighter` at 250 Hz. Dual-licensed MIT or Apache 2.0.

**The numbers** are the README's Benchmarks section and `benchmarks/RESULTS.md`, regenerated from `benchmarks/results/*.csv` (M5) and `benchmarks/results/machines/m1/*.csv` by `python3 benchmarks/report.py` and `python3 benchmarks/readme.py --write`. Never type a number into the README. On the M5 Pro lighter leads OrbStack on 33 of 36 rows; the three it trails are TCP out of a published port (81.7 against 93.1 Gbit/s, a row that moves between runs), GET p99 on a published port (173 against 119 µs) and idle CPU (3 against 2 ms/s, with fewer wakeups). On the M1 it leads on memory, power, start-up, amd64 and the share's file work and trails on the share's installs and on own-disk ripgrep and copy-tree; section 3 has those numbers.

## 2. How the work is done

**Machines.** The M5 Pro (18 cores, 48 GB; Nick's daily machine) is where code is written, gates run and the M5 record is taken. The M1 (8 cores, 8 GB, `admin@100.125.161.101` over Tailscale; on the home LAN it is `192.168.50.21`) is the small-Mac reference and the second record machine. The M1 is a stock Mac in the one way that matters most: `kern.maxfilesperproc` is 10,240 there against 184,320 on the M5 (macOS scales it with RAM), so the share server's descriptor budget is about 8k on the M1 against 147k, and any share behaviour that depends on holding files open shows on the M1 first. Every stock 8 GB Mac is an M1 in this respect.

**The daily driver.** Nick runs lighter as his Docker on the M5 from the checkout: `/usr/local/bin/lighter` is a 67-byte wrapper that execs `target/release/lighter`, and the machine boots `guest/out/Image` and `guest/out/rootfs.ext4`. Three consequences. `cargo build --release` strips the hypervisor entitlement, so after any release build run `make sign PROFILE=release` or the next start fails at `doctor`. A `guest/out/rootfs.ext4` whose init dies takes the daily driver down at its next start (its private copy is an APFS clone refreshed whenever the master changes), and the daily driver is the only Docker on the machine, so it cannot rebuild the rootfs that broke it; OrbStack is installed as the fallback build daemon (`orb start`, `docker context use orbstack`, build, `orb stop`, and then quit OrbStack fully, see the traps). And never stop the daily driver without being told; the gates and records need the machine alone, so ask.

**Gates.** `scripts/gates/run-all.sh` runs the twelve milestone gates (m1 boot, m2 devices, m3 network/vsock/docker/streams/publish, m4 filesystem, m5 speed, m6 memory, m7 x86-64, m8 daily driver) and prints what each cost; about eight minutes. Each gate boots its own machine under a private `LIGHTER_HOME`. m5 refuses to measure while another VM runs (the daily driver, OrbStack's helper, colima), by design. The rule is: every commit green on all twelve before it is pushed to `dev`; the release commit green on the exact head that is packaged.

**Records.** A record is `benchmarks/run.sh` for the lighter target: the share stage (all 21 cases), the own-disk stage (the seven storage cases with `--where guest`) and the amd64 stage (`--arch amd64 --where guest`, four cases); the `.tree` stamps beside the CSVs carry the commit and the artifact hashes and are written `-dirty` because the record rewrites tracked files, so set `commit=` by hand to the clean commit. `scripts/records/record-m5.sh` runs the first two stages on the M5 (append the amd64 stage as the worklog rows show). `scripts/records/record-m1.sh` ships a runner to the M1 over ssh: it restores the tracked result files, fast-forwards to `origin/dev`, builds the CLI and the bench example, copies `Image`, `rootfs.ext4` and `lighter-agent` from `~/m5-artifacts` (rsync them there from the M5 first; the rebuild through colima stays as the fallback), stops colima, Docker Desktop and OrbStack, waits for the host's indexers to be quiet for a minute, and runs the stages; results come back by `rsync` into `benchmarks/results/machines/m1/`. Rules that came from pain: a record is for a release candidate, with every loose end closed first, never a way to find out; the machine must be alone (on 2026-09-06 two other agent sessions on the M5 took a third off the TCP rows and the record was redone); a record must not follow a kernel or rootfs build on the same host; and the `footprint` tool can return the guest's whole size for one sample (16384 MiB once), so a memory peak that equals the configured RAM is a rerun of the stage, not a number.

**A/Bs.** The harness takes `--cases`, `--reps`, `--label` (a separate CSV), `--where guest`, `--arch amd64`; the VMM takes `LIGHTER_VIRTIO_MEM=0|<MiB>` (no range, or a base by hand), `LIGHTER_CMDLINE_EXTRA` (appended to the guest command line), `LIGHTER_MEMORY_STEER=0`, `LIGHTER_STREAM_THREADS=1`, `LIGHTER_SOCKMAP=0`, `LIGHTER_FS_FD_BUDGET=<n>`; `guest/kernel/build.sh` takes `LIGHTER_KERNEL_ONLY=250|1000|trace` (the trace kernel has ftrace for hunting wakeups). One clean A/B whose medians agree within the machine's day-to-day noise is an answer; repeating runs on a busy machine is not.

**Writing it down.** Every experiment is a row in `docs/worklog.md`: `| date | area | what was tried | result | verdict |`, one line, never hard-wrapped, with the numbers. Commits are by path (`git add <files>`), never `git add -A`, because a record in flight has rewritten tracked CSVs. No AI attribution anywhere: no `Co-Authored-By` trailers, no generated-with lines in commits, PRs or code.

## 3. Open work, in the order I would take it

### 3.1 The M1's share installs are behind OrbStack

The one place lighter does not beat OrbStack on the M1's record of 2026-09-06 that matters to a user: `npm ci` on the share 11.73 s against 11.25, `pnpm install` 6.63 against 5.91, `yarn install` 13.41 against 10.43; on the guest's own disk `ripgrep` 203 ms against 143 and `cp -a` 4.43 s against 2.49. The same rows on 5 September (0.3.0, no range) read 11.62 / 6.01 / 10.63 on the share and 137 ms / 3.08 s on the own disk, so the share yarn and the own-disk tree cases are also worse than lighter's own previous record on that machine, while ripgrep and copy-tree on the share are back at their 5 September shape (180 ms, 5.5 s) after the day's fixes. One inconsistency to know about: the worklog row for the M1's release record (2026-09-06, "record", "the M1's release record on 528d242") quotes share pnpm 6.09 and yarn 10.49 and after-install memory 1078 / 1058, while the CSVs committed on the release commit read 6.63, 13.41 and 947 / 944; the CSVs are what the README was generated from and are authoritative, and the row was most likely written from a stage that was then taken again. A third rep of each install case in that record is the lowest (npm 11.0, pnpm 6.6, yarn 12.2), which points at cache state rather than a steady gap; the medians are what the README shows.

What is known. The day's work found and fixed two mechanisms on the 4 GiB guest: the balloon standing through the next container's run (starving the page cache) and the range's blocks all onlined movable (a 1 GiB base holding three installs' slab, reclaimed on every pass). Both are in the worklog with numbers by knob (rows of 2026-09-06 under "memory"). What remains is smaller and different in kind. The 4 September row on the descriptor budget says the budget is not the gap: at 6144 descriptors the install pair cost 0.4 s, and the per-operation profile has the M1 level with the M5 on create, lookup, rename and mkdir and paying double on write (5.5 against 2.7 µs), unlink (22.8 against 11.2) and readdir (61 against 50), which are the operations that take the apply queue's locks, on a machine whose eight cores are all vCPUs. The share server is `crates/lighter-fs/src/{server,inode}.rs`; the apply queue and its lanes are described in `docs/architecture.md` under the filesystem section, and the worklog rows of 2026-09-03 and 04 on "storage" are the measurements.

A way in. First, a clean A/B on the M1 of `BENCH_CPUS=6` against 8: if the installs improve with two cores left to the Mac, the share server is being starved by the vCPUs and the answer is scheduling (the idle poll window `idle.poll_ns`, `config::idle_poll_ns`, is already 50 µs when the vCPUs fill the cores). Second, `LIGHTER_FS_STATS=1` (the server prints its per-operation profile; see the 2026-09-04 rows for how it was read) on the yarn install alone, M1 against M5, to see which operation grew since 5 September; yarn's install is mostly clones and unlinks. Third, the kernel zone: the auto-movable policy at a ratio of one gives the 4 GiB guest 2 GiB of kernel memory; a ratio of 50 (`LIGHTER_CMDLINE_EXTRA="memory_hotplug.auto_movable_ratio=50"`) gives it more, at the cost of idle savings, and is a one-run A/B. Estimate: one to two days on the M1, with the M5 free for building.

### 3.2 The M5's memory after an install

The memory table's "15 s / 60 s after an `npm ci` ends" rows on the M5 read 1143 and 1174 MiB in the release record, against 767 and 773 at noon the same day on the all-movable tree with the old release path, and 2114 for OrbStack. Two changes landed between the two readings and each contributes: the audit follow-up's release path replaces the mapping of every reported run (so pages the guest reuses are charged again, correctly, where before they stayed uncounted), and the auto-movable policy leaves blocks that came up as kernel memory plugged for as long as they hold an unmovable page (m6 measured 384 MiB of them after a container left, and bounds the residue at 768 MiB). A standalone run of the memory case on a fresh guest read 611 MiB after, so the in-suite number carries ten cases' worth of retained slab and cache.

A way in. Two one-run A/Bs on the M5 alone, full share stage each (the memory case's number depends on what ran before it): `LIGHTER_CMDLINE_EXTRA="memory_hotplug.online_policy=contig-zones"` reverts the onlining to all-movable and isolates the policy's share; the release path has no knob any more, so the second arm needs `crates/lighter-vmm/src/memory.rs::release` given back a temporary `LIGHTER_RELEASE=reusable` branch for the measurement. If the policy is most of it, a higher ratio on large guests is a one-line experiment, but it is a second policy by another name, which Nick has said he does not want; if the release path is most of it, the number is honest and the README's memory intro should say what the after rows contain. Estimate: half a day.

### 3.3 Steering that scales with the guest

Seen on the daily driver after the release: 24 GiB configured, three compose stacks, the Mac at 7.8 of 9.2 GB of swap under a dozen agent sessions. The process's footprint read 16979 MiB at one moment and a peak of 26 GB against 24 GiB of guest RAM, and the steering moved the balloon between 224 and 512 MiB: `memory_policy.rs` raises the target by `INFLATE_STEP_BYTES` (32 MiB) a second while the host compresses, under `STEER_CAP_FRACTION` (an eighth of RAM), and eases by the same step when quiet. On a 24 GiB guest whose cache three stacks have filled that is a teaspoon; the pressure levels (`WARN_FRACTION` a quarter, `CRITICAL_FRACTION` a half) only fire when macOS reports them, which it does late. The machine worked throughout; the Mac paid with swap.

A way in. Scale the step with the guest (a 256th of RAM a second, say) and let the cap rise with the pressure level; and consider shrinking the range under host pressure even while containers run (today `guest_sizes` keeps the range whole for any container; the kernel migrates cache out of a movable block when asked to offline it, which is exactly the response wanted). The m6 gate's pressure section and `LIGHTER_MEM_TRACE=1` (the guest's free memory and the host's holdings every second, to the log) are the instruments. Estimate: one day, plus a day of the daily driver on the build, which is the only honest test of it.

### 3.4 The region count under the fresh-mapping release path

With every reported run replaced by a fresh anonymous mapping, the VMM process holds about 19,000 memory regions on a busy daily driver (`vmmap --summary <pid>`). Yesterday's measurement (worklog, 2026-09-05, "memory", the remap rows) had the replacement of reporting's runs take the address map's lock from under a container that was starting at the time (552 to 1131 ms starts). The audit follow-up coalesces adjacent buffers within one reporting request, and a one-run A/B on 2026-09-06 read ten container starts after an install at 141–247 ms against 131–169 on the old path, and installs within noise, so it shipped. Nobody has measured a day of it.

A way in. `LIGHTER_STREAM_TRACE=1` gives the reactor's counters; the number to watch is a container start during the trims after an install (`--cases "npm-install container-start" --reps 10`). If the regions cost, the options are a floor under which reporting's runs go back to `madvise` (the 128 KiB span floor the remap had before the audit change, at the price of a small accounting gap) or merging the fresh mappings back with `mach_vm_remap`. Estimate: half a day to measure, a day if it needs the floor back.

### 3.5 Two network rows that move between runs

TCP out of a published port on the M5 read 94.9 Gbit/s at noon and 81.7 in the release record; GET p99 on a published port 136 and 173 µs; both are the published-port direction through the reactor's `carry_inbound` path (`reactor.rs`, `Phase::AwaitEstablished`, then `Open`). Egress rows are steady. Estimate: a morning with `LIGHTER_STREAM_TRACE=1` and iperf3 on a quiet machine to see whether it is the reactor's single thread (`crate::qos::raise_interactive`, the spin window) or the guest's side (`guest/agent/src/main.rs::forward_inbound`, the sockmap join).

### 3.6 The one-line installer and a developer's wrapper

`scripts/install.sh` ends by symlinking `/usr/local/bin/lighter` (or `~/.local/bin/lighter`) to `$INSTALL_DIR/bin/lighter`, whatever `LIGHTER_INSTALL_DIR` says. On a developer's Mac whose `/usr/local/bin/lighter` is a wrapper onto a checkout, a throwaway install replaces it (it did, on 2026-09-06, and was restored by hand). The fix is small: leave a `/usr/local/bin/lighter` that is not a symlink alone and say so. An hour, with a test that runs the installer twice into two prefixes.

### 3.7 Container start speed without the second kernel

0.4.0 dropped the 1000 Hz kernel (worklog and `docs/architecture.md`, "One kernel, and why it ticks at 250"): it gave container starts 60 ms against 112 on the M5 and took 10 to 20% from the share's installs. `CONFIG_HZ` is compile-time and there is no runtime tick knob, but most of a container start's cost is RCU grace periods ending on the tick, and `rcupdate.rcu_expedited=1` on the guest command line makes every `synchronize_rcu` expedited at the price of IPIs across the vCPUs. It is a one-run A/B with `LIGHTER_CMDLINE_EXTRA` on `--cases "container-start npm-install"`, both machines. Estimate: two hours.

### 3.8 Smaller threads

- *containerd's garbage collector* re-arms its timer forever once it has collected once (four wakeups a second from a collector with nothing to do); init works around it with `startup_delay = "0s"` and `pause_threshold = 0.0`. The upstream issue is drafted (it was in `.logs/containerd-gc-issue.md` on the M5; the substance is the 2026-09-06 "idle CPU" rows) and not yet filed; Nick said he would file it.
- *Activity Monitor's icon.* The machine runs from `~/.lighter/lighter.app` so Activity Monitor shows a name and the flame; Nick reports no flame on his daily driver. The bundle is right (the icns has every size, the plist is sealed, Launch Services resolves the identifier to the bundle); 89 dead registrations from temporary homes were purged and temporary homes no longer register (`crates/lighter-cli/src/bundle.rs::register`). Unverified since: whether Activity Monitor, reopened, shows it now.
- *`lighter doctor` blocks `start` when the `docker` CLI is not on PATH* (`main.rs::start` filters only the docker-context, machine and rosetta findings). A machine is useful without a local CLI (a remote `DOCKER_HOST`); the finding should not block.
- *The M1's record scripts and the smoke script* are now in `scripts/records/`; they were written for one machine each and read best as a record of what a record is, not as a tool anyone else should run unmodified. The smoke script captures `docker run`'s stderr on purpose in some checks and not others; read it before trusting a verdict.
- *`docs/architecture.md`'s memory section* has grown by accretion through the week; it is accurate but long, and the "fourth way" paragraph is due a rewrite now that the design has settled.

## 4. Traps, so they are only paid once

- **Signing.** `cargo build --release` strips the hypervisor entitlement; `make sign PROFILE=release` after every release build before anything starts a machine from `target/release`. The packager builds release and signs a copy, leaving `target/release/lighter` unsigned.
- **A rootfs whose init dies** panics the guest (`Attempted to kill init`) and the daily driver goes with it at its next start; the rootfs cannot then be rebuilt through the daily driver. Every new line in `guest/rootfs/init` (which runs `set -eu`) gets `|| true` or an explicit `|| echo "INIT x=failed"`. Keep the previous `guest/out/rootfs.ext4` aside before a rebuild.
- **The host plugs the range before init runs**, so a hotplug policy written from init in sysfs is read back as set and never applied to a block. Kernel defaults or the command line, never init, for anything the first plug must see.
- **Vsock ports 2375–2383 are all taken** (docker, control, stream, inbound, dns, udp, memory policy, clock, udp-inbound); grep `crates/lighter-vmm/src` for `u32 = 23` before choosing one. The first UDP-inbound port collided with the memory policy's and the wrong listener closed the stream.
- **`orb stop` leaves OrbStack's helper daemon running**, and m5 refuses to measure beside it; quit the app (`osascript -e 'quit app "OrbStack"'`) or kill `OrbStack Helper` before gates or records. The same for colima (`limactl hostagent`) and Docker Desktop (`com.docker.backend`).
- **Another Claude session on the M5** reads as a third off the TCP rows and slower installs; look at `uptime` and `ps -Ao pcpu,comm -r | head` before a record and get the machine alone.
- **A record straight after a kernel or rootfs build** on the same host is worthless (indexers on the build's files); the M1 script waits for them, the M5 has no equivalent yet.
- **The `footprint` tool** can return the guest's whole configured size for one sample; a memory peak equal to the configured RAM is a rerun of the stage.
- **The gates' `LIGHTER_GATE_SHARE`** must be under `$HOME` (only the default share is mounted); `pkill -f` of a chain leaves its children running (use `[b]racket` patterns in `pgrep`, and kill the children); `tail -F` replays old logs at monitor start.
- **The agent's control `sh` command** takes lines of at most 4 KiB; ship a script into the guest as base64 chunks.
- **`git checkout -- benchmarks/results` on a record host mid-record**, or `git add -A`, destroys the only copy of the numbers; the M1 script copies the CSVs aside before restoring.
- **The installer symlinks `/usr/local/bin/lighter`** whatever prefix it was given (3.6).
- **Bash's `$D`** holding `docker -H unix://…` word-splits in bash and not in zsh; the gate and record scripts are bash for that reason. Run them with `bash`, not `sh`, and not from a zsh one-liner.
