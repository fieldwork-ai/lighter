# Running x86-64 containers

`docker run --platform linux/amd64 …` runs under Rosetta. The Mac translates the container's x86-64 code with the same Rosetta that runs Intel Mac apps, at about two thirds of native speed on interpreter-style work and with x86's memory ordering in hardware; the emulator that stands in when Rosetta is not installed runs at about a tenth.

## How it works

Rosetta for Linux is one arm64 binary at `/Library/Apple/usr/libexec/oah/RosettaLinux/rosetta`. When the Mac has it, `lighter start` shares that directory into the guest under the tag `rosetta` and says so on the kernel command line (`lighter.rosetta`); the guest's init mounts it at `/mnt/rosetta` and registers the binary with `binfmt_misc` as the handler for x86-64 ELF files.

The registration uses the `F` flag, and that flag is the whole trick. Without it the kernel resolves the interpreter path at `exec` time, inside the container's mount namespace, where `/mnt/rosetta` does not exist, so every amd64 container fails with a confusing `no such file or directory`. With it the interpreter is opened once, at registration, and the open file is what every later `exec` uses. `O` and `C` open the binary itself with the caller's credentials, which is what lets a setuid program inside a container behave.

Two more things have to be true, and both are lighter's to arrange.

**The file server has to answer for it.** Before it runs anything, Rosetta asks the filesystem it was loaded from a few questions: `ioctl`s of type `0x61` on its own binary. Two of them (`0x22` and `0x25`) expect a 69-byte constant back, one (`0x23`) 128 zero bytes, one (`0x24`) plain success; a server that answers `ENOTTY` gets "Rosetta is only intended to run on Apple Silicon with a macOS host using Virtualization.framework with Rosetta mode enabled". That is what the binary was observed to do (`strace`, then a twenty-line C program issuing the same `ioctl`s, `docs/worklog.md` 2026-09-05); there is no challenge–response and nothing to reverse-engineer. `lighter-fs` answers those four for the Rosetta binary's inode and nothing else (`Server::serve_rosetta`). The constant is Apple's text and is not in this repository: it is in the user's own installed Rosetta, and `lighter-vmm::rosetta::key` finds it there by its SHA-256 among the NUL-terminated strings of that length. A Rosetta that stops carrying it is reported by `lighter doctor`, and amd64 containers run under the emulator until lighter is updated for it.

**Its threads need x86's memory ordering.** Translated x86 code assumes stores become visible in order, which ARM does not promise. Apple silicon can promise it per thread (bit 1 of `ACTLR_EL1`), and Rosetta asks for it itself, with `prctl(PR_SET_MEM_MODEL, PR_SET_MEM_MODEL_TSO)`, the interface Hector Martin and Apple both proposed for Linux in April 2024. Kernel patch 0023 implements it: the setting belongs to the thread, is inherited across `fork` and `clone`, reset by `exec`, and written to the register only when the incoming thread's differs from what the CPU last had. Native threads keep ARM's ordering, so they pay nothing; switching the whole machine instead cost native `memcpy` a quarter of its bandwidth. A message-passing litmus test reorders on native threads and never under Rosetta, which is how this was checked rather than assumed.

## Without Rosetta

A Mac without Rosetta installed (it is a one-time Apple download) runs amd64 containers under `qemu-x86_64` instead, registered the same way; slower, and correct. `lighter doctor` says which of the two a machine will use, and `lighter rosetta --install` runs Apple's installer (`softwareupdate --install-rosetta`).

## What it costs

Measured on an M5 Pro (`docs/worklog.md`, 2026-09-05): a Python `hashlib.sha256` loop at 660k blocks a second native, 147–152k under Rosetta and 56k under qemu; a plain interpreter loop at 80 ms native, 152–161 ms under Rosetta and 1443 ms under qemu. For the common cases — an amd64 image that mostly waits on the network or the filesystem, a database, a build tool with an ARM version you have not switched to yet — the difference from native is smaller than those numbers suggest, because the translated code is not what is slow. Node 22 and PostgreSQL 16 amd64 images start and work.

## Why not Virtualization.framework

Apple's own way to offer Rosetta to a Linux guest is `VZLinuxRosettaDirectoryShare`, which exists only for Virtualization.framework. lighter ran on that framework for a day (branch `framework`), and measured two things it cannot do: return memory the guest has given back to macOS (the footprint only ever grows), and answer a synchronous filesystem request in under about 33 µs, against 3–5 µs on lighter's own device. Both are structural, neither is fixable from outside Apple's helper process, and Rosetta turned out not to need the framework: a constant the user already has, and one bit the hypervisor exposes. OrbStack, for the record, runs its own VMM on Hypervisor.framework too.
