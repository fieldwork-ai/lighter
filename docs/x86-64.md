# Running x86-64 containers

`docker run --platform linux/amd64 …` works. It runs under emulation, not Rosetta, and this is the note explaining why — because Rosetta would be two to three times faster and the question will keep coming up.

## What was tried

Rosetta for Linux is a single arm64 binary at `/Library/Apple/usr/libexec/oah/RosettaLinux/rosetta`. A VM is supposed to expose that directory over virtio-fs; the guest registers the binary as a `binfmt_misc` handler for x86-64 ELFs, and it translates them.

lighter can do the sharing part, and does it correctly. Sharing that directory and running the binary inside the guest gets as far as:

```
rosetta error: Rosetta is only intended to run on Apple Silicon with a macOS host
using Virtualization.framework with Rosetta mode enabled
Trace/breakpoint trap
```

The binary is there, it is readable, it executes, and it declines.

## Why it declines

Rosetta checks that it is running under Apple's **Virtualization.framework**, and does it by issuing undocumented `ioctl`s on the virtio-fs device it was loaded from. Current versions use a challenge-response with a secret that only Apple's framework holds. `VZLinuxRosettaDirectoryShare` is the sanctioned way to satisfy that, and it exists only for Virtualization.framework — a higher-level API that does not let you supply your own virtual devices, which is the entire reason this project is built on Hypervisor.framework instead.

So the check is not a bug on our side and not something a better virtio-fs implementation reaches. It is a licence restriction with a technical lock on it.

It is possible to answer the handshake by capturing the secret from a real Virtualization.framework session and replaying it. libkrun did exactly that and then removed it, in a commit titled "macos: drop Rosetta support". lighter will not carry that code: it circumvents a technical measure enforcing Apple's licence terms, and no amount of performance is worth shipping that in a repository people are invited to use.

## What is here instead

`qemu-x86_64`, registered through `binfmt_misc` at boot, in `guest/rootfs/init`.

The registration uses the `F` flag, and that flag is the whole trick. Without it the kernel resolves the interpreter path at `exec` time — inside the container's mount namespace, where `/usr/bin/qemu-x86_64` does not exist, so every amd64 container fails with a confusing `no such file or directory`. With it, the interpreter is opened once at registration and the open file is what every later `exec` uses. This is the same mechanism `tonistiigi/binfmt` relies on.

## What this costs

Emulation, so roughly a third of native speed on CPU-bound work, against Rosetta's 70–80%. For the common cases — an amd64 image that mostly waits on the network or the filesystem, a database, a build tool with an ARM version you have not switched to yet — the difference is much smaller than that number suggests, because the emulator is not what is slow.

If Apple ever exposes Rosetta to Hypervisor.framework, this becomes a small change: the sharing already works, and only the handler registration would move.
