# Filesystem event-loss recovery, 2026-09-07

The first release-source qualification on M5 failed the watch-latency case: its first request received no visible reply within 30 seconds. The numeric storage cases completed. M1 passed the same source qualification. The M5 failure remains an invalid qualification, not a slow timing sample.

Three focused storage-sequence repetitions subsequently completed, with first watch round trips of 153, 798 and 80 ms. A 20-round continuous test also passed. These successes did not explain the failure.

A stronger probe cached 1,000 distinct empty files before asking the host to update each. M1 completed all 1,000, with a 48 ms maximum. M5 failed on the first file: the host-side request and reply both contained `1`, but the guest continued reading an empty file for 30 seconds. A private diagnostic VMM logged 56,656 filesystem events during the run, including repeated flag value `3` (`MustScanSubDirs | UserDropped`). The reply's own path never appeared. The stream was also receiving delayed events from the preceding VM's package tree.

Apple requires a recursive rescan when event detail is lost; a notification naming a directory does not describe every changed descendant. Our callback ignored the flags and invalidated only the reported path and its parent. That left cached descendants valid for up to five minutes. Independently, our bounded notification queue discarded its oldest message on overflow, causing the same loss of information. [Apple's event-loss requirements](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html).

The recovery path now:

- Turns a lost-detail callback into one complete reset for that share. A moved or removed watch root also permanently selects conservative timeouts until restart, including if feature negotiation races the root change.
- Replaces an overflowing notification backlog with a complete reset, followed by newer messages. The queue remains bounded; a reset subsumes earlier individual invalidations.
- Negotiates complete reset support separately from individual notifications. Older kernels use the existing conservative timeouts.
- Uses the guest's dentry epoch to withdraw positive and negative name caches. A request-version barrier expires attributes and open-file data, including responses that began before the reset. Contents are refreshed even when host writes preserve size and mtime.
- Invalidates existing mappings explicitly, refreshing size so a host-truncated mapping faults correctly. The kernel pins inodes while traversing its cache, following its existing cache-walk pattern, without allocating a list proportional to the cache size.

The signed hardware probe creates and mutates its fixtures from the VMM process itself, making FSEvents' IgnoreSelf deliberately hide the individual writes. Its control files stay outside the watched share, and the probe disables the hot-directory cooldown so setup activity cannot give the initial lookups zero cache validity. It verifies that the guest still reads stale data for a full second, then injects either a reset or queue overflow. Both modes refresh an open descriptor, path reads, an existing mapping, an empty file, negative lookups, deleted and renamed names, and directory listings. The same-size/same-mtime fixture verifies data invalidation; a separate truncated mapping must receive SIGBUS. These checks passed on M5 and are now part of the filesystem gate. Unit tests exercise actual callback flag handling, permanent fallback after losing the watch root, reset ordering and backlog overflow.

Repeating the real M5 storage sequence followed by the 1,000-file probe completed all updates with the recovery path active. Reset warnings confirm that macOS again lost event detail. The maximum round trip was 1,429 ms under this overload. That is recovery evidence, not a claim of sub-100-ms visibility under all host conditions. A stalled event daemon can still delay notification delivery; the timeout backstop remains finite.

A later M5 qualification exposed a probe precondition failure: its empty file was already fresh before the injected reset. The initial probe created fixtures and control files from an external host process, whose events can invalidate caches or make the server hand out zero validity during its hot-directory cooldown. The isolated setup above preserves the full stale-control assertion and every recovery assertion; five consecutive M5 runs passed both reset and overflow modes. This changes test setup only, not the production runtime.

All initial failure logs and diagnostic runs are retained privately. Full share, guest-disk and amd64 records were refreshed on both Macs at runtime `5f3223e`; the earlier `38bfab4` measurements describe the preceding runtime. Watcher integration tests also distinguish precise events from loss-of-detail rescans. A rescan only covers a control write if it was received after that write completed; the teardown stress test runs separately from delivery and IgnoreSelf checks. Five repeated watcher-test runs passed. Exact release-head qualification is repeated after these test-only corrections.

After the release archive passed qualification, the formula/worklog pre-push check exposed another unit-test timing failure under the full filesystem suite. Thirty isolated IgnoreSelf repetitions passed, but a diagnostic full-suite run saw the precise external `touched` event arrive about 13.64 seconds after its write: 3.64 seconds after the unchanged ten-second assertion deadline. The failure was retained even though the later event proved delivery. Readiness events continued arriving during that interval; this was delayed delivery, not evidence of a silent lost-detail event.

Requesting a synchronous FSEvents flush did not remove every deadline failure, so that attempt was rejected. The OS-backed watcher checks now run in a separate integration-test executable, after the library’s inode/cache stress tests finish. This removes the suite’s own concurrent filesystem load while retaining the original ten-second assertions and ordinary asynchronous delivery; no test or production path forces an event flush. Five consecutive complete filesystem suites passed with that separation. The callback-flags unit test remains beside the implementation, and the hardware watch and cache-recovery probes retain their existing assertions. The change is confined to test code; the released runtime and its full benchmark records are unchanged. The observed delay remains a real limitation under heavy host filesystem load, not a latency guarantee improved by test isolation. [Apple’s event-delivery guidance](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html) explains that notification latency is nondeterministic.


## Delivery stalls and independent expiry

The subsequent exact-head qualification on M1 passed all twelve gates, but M5's watch case timed out after 30 seconds with the host request and reply both present. The later qualification is invalid. The existing release candidate was marked as a prerelease and the Homebrew PR returned to draft while this was investigated.

Passive callback traces reproduced unassisted first-update delays of 30.53 and 34.42 seconds. In each, the lost-detail callback itself arrived late; the reset followed immediately and made the guest fresh. Other diagnostic runs received no useful callback within 120 seconds. Raising dispatch-queue priority did not fix this. A periodic asynchronous FSEvents flush still produced an 83.24-second first update, so neither experiment was retained. One 44.63-second trace overlapped a diagnostic signal and cannot establish unassisted recovery.

A prospectively alternating fresh/reused-directory experiment completed all five runs, including both reused controls, with first updates between 188 and 1,430 ms. One bundled-helper run also passed. These successes do not establish that fresh paths or application bundles fix the intermittent delay. The OS service's underlying delay remains unexplained.

The production candidate therefore caps notification-backed name and attribute leases at twenty seconds, instead of five minutes for positive answers and thirty seconds for negative answers. Normal notifications still withdraw answers earlier. This is a cache-lease backstop, not a hard wall-clock guarantee for filesystem operations. Expiry revalidates ordinary names and attributes; existing mappings and writes preserving both size and mtime still require notification-driven invalidation.

A controlled hardware probe makes the host mutations inside the VMM process, where IgnoreSelf suppresses notifications. It first proves a full second of stale reads, then waits for ordinary expiry without injecting a reset. The original leases fail the new freshness assertion. The ten-second candidate refreshes the empty file through both an already-open descriptor and its path, negative lookups, deleted and renamed names, and directory listings. Its notification counter must remain unchanged between mutation and the freshness check; the observed pass took 10.05 seconds. The reset and overflow cases separately force long leases, retaining all existing same-size/same-mtime, mmap and truncation assertions so expiry cannot stand in for a reset.

Five-second leases were also tested and rejected: two M1 runs produced search medians of 782 and 762 ms against a 1,233-ms native baseline, below the unchanged 200% speed floor. The ten-second comparison also failed the search floor: medians were 1,419 and 1,176 ms versus the surrounding controls at 176 and 153 ms. Twenty-second leases recovered the search floor (299 and 203 ms), but the full sequence exposed slower copy medians (8,312 and 9,288 ms versus 5,586 and 5,380 ms). These are reasons to continue investigating, not evidence that the longer setting has no cost.

A separate small-memory build exposed compression-driven balloon reclamation competing with guest demand. The host policy now yields that heuristic to guest demand while preserving actual host-pressure floors. The subsequent alternating long/twenty/twenty/long comparison below tests the interaction before selecting the final cache setting. Exact-head qualification and refreshed full benchmarks remain required before a replacement archive. These changes preserve the memory-allocation correction.

## Selected profile and observed limits

The controlled M1 long/twenty/twenty/long comparison with guest-aware compression steering retained all ordered samples. Cached-search run medians were 259/369/345/199 ms, giving a 128-ms (+55.9%) increase for twenty-second leases. Both twenty-second arms still cleared the existing 200% native-speed floor. Copy medians were 6,563/6,562/8,145/5,452 ms: +22.4% in the median of run medians, with overlap and substantial variation. Smaller differences in other cases are not presented as general performance gains. Twenty seconds is the shortest tested setting that cleared the search floor in both arms, and is retained with its cost documented.

The actual twenty-second defaults passed the notification-free probe after 20.051 seconds. In the initial `297f622` M5 qualification, the watch samples were 20.004 seconds, 525 ms and 2 ms. The first shows the expiry fallback working during delayed notification delivery; the 525-ms median still failed the unchanged 100-ms budget, so the qualification remains invalid despite the other eleven gates passing. Full benchmark results are separate observations and do not replace that failure. Exact release-source qualification is required before packaging. No queue-priority, periodic-flush or fresh-directory workaround was adopted, and the underlying macOS callback delay is not claimed fixed.

One separately scheduled complete M5 qualification after the full benchmarks passed all twelve gates in 486 seconds on the same runtime, including watch samples of 1,216/1/2 ms. Workspace (321) and signed hypervisor (15) tests also passed. Both the failed and confirmation speed samples are retained. This confirmation does not replace the initial failure or establish deterministic host event delivery.

## Exact metadata qualification and independent delivery trace

The following exact-source qualification on `2e2bce5` passed all twelve gates on M1 (506 seconds), plus 321 workspace and 15 signed hypervisor tests on both hosts. M5 passed eleven gates but failed the unchanged watch median again: 20,004/445/1 ms. Neither that run nor the earlier failed run is a passing M5 qualification. The full benchmark records remain measurements of the same production runtime in `297f622`; metadata commit `2e2bce5` did not change it.

A separate M5 diagnostic timestamped request/reply vnode changes with kqueue, notifications in an independent FSEvents process, and the VMM callback before it entered the original observer. The host answered the first request in 2.42 ms. The external notification arrived 20.628 seconds after the first reply, and the VMM notification 21.243 seconds after it. The guest had already refreshed the first reply through its twenty-second lease; the second reply completed about 0.38 ms after the VMM callback began. Guest round trips were 20,003/1,240/2 ms. No original observer callback exceeded the diagnostic's 100 ms threshold. This localizes the long wait before the VMM observer; it does not establish why macOS delayed/coalesced delivery. The independent observer adds its own event-service load, so these are diagnostic timestamps, not performance records.

Preventing App Nap did not resolve the failure. The predeclared control/active/active/control trial produced 20,003/697/1; 20,005/960/1; 20,002/1,769/2; and 785/1/2 ms. Both active arms failed the existing median threshold, and no activity assertion was added to production.

A separate uninstrumented 0.4.0/current/current/0.4.0 comparison produced 188/2/2; 1,885/1/2; 2,918/1/2; and 1,979/2/2 ms. All four passed the median threshold. That comparison did not reproduce the earlier failures and cannot establish a regression or its absence. First-update times overlap and vary substantially. Matching binaries and guest artifacts were selected for every arm; corrected provenance distinguishes the harness commit from the runtime commit.

A bare/bundled/bundled/bare comparison of the same example, with both variants ad-hoc signed using hardened-runtime options, produced 20003/395/2; 20000/355/2; 332/2/2; 1256/2/2 ms. A bundled arm also failed, so bundle identity did not establish a fix. The first bare arm overlapped documentation read/hash work and is not a quiet control. No bundle or runtime change was selected. Raw follow-up samples and diagnostic sources preserve all outcomes and conditions.

The latest candidate still requires a replacement signed/notarized archive and tests from that exact archive. The existing `v0.4.1` prerelease is the earlier `19c0786` candidate. The dev→main and Homebrew pull requests remain drafts. These limitations and the failed M5 qualifications are retained for release review.
