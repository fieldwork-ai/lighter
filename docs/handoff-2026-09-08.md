## Evidence and limits

[Qualification](release-0.5.0.md), final-artifact records
and [benchmark analysis](../benchmarks/RELEASE-0.5.0.md) contain the results.
Both Macs pass 339 workspace tests, 15 signed hypervisor tests, twelve hardware
gates and the expanded socket stress tests. The kind matrix covers arm64 IPv4
one- and two-node clusters; it is not a Kubernetes conformance certification.

Three full benchmark suites per host, five fresh same-build storage runs,
ABBA and follow-up BAAB comparisons, native measurements and fresh installed
competitors are retained. README tables use the documented selected records.
M1 Yarn and M5 share copying remain possible costs; there is no general speedup
claim. Failed setup and dependent competitor results are excluded explicitly,
with raw attempts preserved. The historical fseventsd incident was not reproduced.

The final archive passes fresh smoke, 0.4.1 and private 0.4.2 migration,
activation/failed-boot rollback and two-node kind persistence on both Macs.
M1 covers real login-service activation and a Homebrew upgrade. M1 input and
private kind-path provisioning failures are preserved; its continuation verifies
identical source and every input hash before completing the remaining stages.
The separate development-layout lifecycle test does not substitute for release
signature verification.

## Publication after review

1. Review and merge the dev → main PR. Check the final PR CI result. Main merge
   remains the review boundary; neither release publication nor tap merge is
   automatic.
2. Confirm the merged tree contains only the tested runtime and subsequent
   evidence/formula changes. If runtime or guest code changes during review,
   requalify and rebuild; do not publish the old artifacts as that new runtime.
3. Confirm the draft `v0.5.0` release has exactly the archive and bootstrap above,
   with their expected hashes. Point the draft target at the reviewed merged
   commit and publish it as latest. GitHub supports
   `gh release edit v0.5.0 --target <merged-commit> --draft=false --latest`.
   Verify the resulting tag resolves to the reviewed commit. Do not overwrite
   an existing published tag or asset.
4. Download both published assets through their public release URLs into a
   temporary directory and compare SHA256 against the values above. The new
   installer requires the standalone bootstrap, so coordinate merge and
   publication without leaving main's installer pointing at missing assets.
5. Make the existing tap PR ready only after both public downloads verify.
   Its retained branch name is `release/0.4.2`; its formula is 0.5.0 with the
   archive checksum above. Merge it through normal review.
6. Install the public release on the M5 daily driver, preserving the existing
   16 GiB configuration, data and stopped state. Confirm ownership, version,
   signed manifest and Docker endpoint. Do not silently start its VM.
